0结论先行

你的直觉方向是对的，但不能笼统地说"V307 不如 H417"。分三个维度看：
  • hal_gpio 的实现质量 —— H417 明显更好。差异不是风格，是抽象在说谎：V307 的 af_num 参数被彻底丢弃，速度档位语义倒挂。
  • Config.h 的板级配置完整度 —— 对各自那块板而言，V307 更差。而且我把 Config.h 与 电路.txt 的原理图网表做了交叉核对，发现了一处会造成实际故障的引脚冲突（见第 5.1 节）。
  • 外设实例抽象 —— V307 反而更好。H417 把 SPI2、DMA2_Channel1、DMA_MuxChannel9、请求号 66 直接写死在 mic_hum.c 里；V307 用 I2S2_SPI_INSTANCE 这类宏封起来了。

而且——两份实现是"同源分叉"：hal_gpio.h 两份逐字节相同，hal_gpio.c 有 80% 相同。所以这不是"两个人写了两种风格"，而是一份代码移植到 V307 时，把 H417 有硬件支撑的部分留成了空壳。

2.1 hal_gpio.h —— 完全相同

3代码层问题（9 条）

3.1 缺陷af_num 参数被彻底丢弃

这是最硬的一条证据。VOICE_V307/Common/hal_gpio.c:42-44：

    // hal_gpio.c:42  空 if 块 —— 什么也不做
    if (mode == HAL_GPIO_MODE_AF_PP || mode == HAL_GPIO_MODE_AF_OD || mode == HAL_GPIO_MODE_AF_INPUT) {

    }

对比 EXAM/GPIO/VOICE/Common/hal_gpio.c:42-44：

    if (mode == HAL_GPIO_MODE_AF_PP || mode == HAL_GPIO_MODE_AF_OD || mode == HAL_GPIO_MODE_AF_INPUT) {
        GPIO_PinAFConfig(gpio, pin, af_num);      // ← 真实生效
    }

为什么 V307 只能留空：VOICE_V307/Peripheral/inc/ 下不存在 GPIO_PinAFConfig（已 grep 确认）。V307 的复用功能由 GPIO_Mode 直接决定（AF_PP/AF_OD/AF_INPUT 三种），无法选择同一引脚的第二个复用功能。

后果不是"少个功能"，而是"接口在骗人" 任何调用者写 Hal_GPIO_Init(pin, HAL_GPIO_MODE_AF_PP, speed, 5)，会以为自己选了 AF5。 实际上 5 被忽略，拿到的是该引脚的默认复用功能。 V307_PERIPHERAL 的手册查下来：PA15/PB3 在 V307 上的默认复用是 JTDI/JNTRST（JTAG），不是 I2S3。 所以 I2S3 那三个引脚能不能真的工作，取决于 V307 是否对这三个脚实现了"按 Mode 选 AF"的隐式重映射 —— 这一点从代码看不出保证，建议实测波形确认。

3.2 缺陷Config.h 里 I2S2_GPIO_AF 0 是假值

Config.h:22 和 :38 分别定义 I2S2_GPIO_AF 0、I2S3_GPIO_AF 0，随后被 mic_hum.c:484-491 当作参数传入 Hal_GPIO_Init。

而 H417 版是 GPIO_AF5 / GPIO_AF6 —— 真值，且真的被用上。

这是个"看着可移植、实际不可移植"的配置项。更糟的是它伪装成了与 H417 同构的接口，下一个接手的人会以为改这个值就能换复用功能。

3.3 缺陷速度档位语义倒挂，4 档只有 3 个实值

// V307 的底层枚举（ch32v30x_gpio.h:24-26）
GPIO_Speed_10MHz = 1, GPIO_Speed_2MHz = 2, GPIO_Speed_50MHz = 3

// H417 的底层枚举（ch32h417_gpio.h:25-28）
GPIO_Speed_Low = 0, GPIO_Speed_Medium = 1, GPIO_Speed_High = 2, GPIO_Speed_Very_High = 3

// V307 的映射（hal_gpio.c:57-62）
HAL_GPIO_SPEED_LOW       → GPIO_Speed_10MHz
HAL_GPIO_SPEED_MEDIUM    → GPIO_Speed_2MHz      // ← 比 LOW 慢 5 倍
HAL_GPIO_SPEED_HIGH      → GPIO_Speed_50MHz
default (VERY_HIGH)      → GPIO_Speed_50MHz     // ← 与 HIGH 相同

调用 HAL_GPIO_SPEED_LOW 本意是"最慢、EMI 最小"，实际拿到 10 MHz；MEDIUM 拿到 2 MHz。同时 HIGH 与 VERY_HIGH 完全等价。

当前实际影响：低 项目里所有调用都传 HAL_GPIO_SPEED_HIGH 或 VERY_HIGH（都映射到 50 MHz），LOW/MEDIUM 从未被使用。 但如果将来为了降 EMI 或降功耗去用 LOW，会得到反效果。这是典型的"埋着的地雷"。

3.4 缺陷引脚掩码静默截断（两端共有）

// hal_gpio.c:34（两份都有）
uint16_t pin_mask = 1UL << pin;      // pin 来自 enc & 0xFFFF, 可以是 0~65535

若 pin > 15（比如手误写成 HAL_GPIO_PIN(1, 20)），1UL << 20 = 0x100000 截断成 uint16_t 后是 0。于是 GPIO_Init 收到 GPIO_Pin = 0，静默什么都不做，没有任何告警。

Hal_GPIO_Read 同理：GPIO_ReadInputDataBit(port, 1UL << pin) 把 32 位常量传进 uint16_t 形参。

另外 pin_enc 编码占 16 位端口 + 16 位引脚，但没有任何 API 校验合法性；且 HAL_GPIO_PORT() 返回 uint8_t，而编码允许 port 到 16 位——约定与实际不匹配。

3.5 异味EXTI 全量接管，堵死其它模块

hal_gpio.c:159-220 无条件定义了 EXTI0..EXTI4、EXTI9_5、EXTI15_10 七个强符号。

实测后果（obj/TEST-INMP441-DOUBLE.map 第 2886~2906 行）：这 7 个处理函数 + s_exti_callback[16] 数组全部进入最终镜像——因为它们被中断向量表 .vector 直接引用，--gc-sections 收不掉。

而全项目没有任何地方调用过 Hal_GPIO_IRQ_*（已 grep 确认，H417 侧也一样）。

真正的问题不是那点 flash，而是"没有退路" 集成任何自带 EXTI 处理函数的第三方驱动（SD 卡检测、ADS1115 ALERT 中断、蓝牙 STATE 中断）时，会直接重复符号链接失败。 被迫绕道 HAL 的 void(*)(void) 回调——而这个回调签名没有参数，无法区分是哪条线触发。

3.6 缺陷回调表非 volatile、无重入保护（两端共有）

static void (*s_exti_callback[16])(void) = {NULL};   // 缺 volatile
void Hal_GPIO_IRQ_Config(...) {
    s_exti_callback[pin] = callback;                 // 在 EXTI_Init 之前写
    GPIO_EXTILineConfig(...);  EXTI_Init(...);  NVIC_EnableIRQ(...);
}

两个问题：

  • 数组非 volatile，编译器理论上可以把它缓存在寄存器里（虽然本工程 -Os 下大概率不会）。
  • 回调先注册再使能线路。如果在 EXTI_Init 与 NVIC_EnableIRQ 之间发生了残留 pending 位，回调会在"注册完成但配置未完成"的窗口里被调用。

安全顺序应是：EXTI_ClearITPendingBit → EXTI_Init → 写回调 → NVIC_EnableIRQ。

3.7 异味时钟使能分裂在两个文件

GPIO_ClockEnable 在 hal_gpio.c，而 SPI_ClockEnable / DMA_ClockEnable / AFIO_ClockEnable 在 Config.c。这直接导致 mic_hum.c:469-478 开头出现连续 10 行 ClockEnable —— 这种"仪式感"代码就是设计缺陷的外在症状。

3.8 异味芯片寄存器裸操作泄漏到业务层

// mic_hum.c:481
AFIO->PCFR1 = (AFIO->PCFR1 & ~AFIO_PCFR1_SWJ_CFG) | AFIO_PCFR1_SWJ_CFG_JTAGDISABLE;

为了给 I2S3 腾出 PA15/PB3，mic_hum.c（业务层）直接读写 AFIO 寄存器。这本该是 Hal_AFIO_DisableJTAG() 这种 HAL 函数的职责。

另外这个读改写在写之前没有关中断，也没有考虑"如果将来需要保留 JTAG"的分支。

4.3 异味没有帧协议层

// voice_protocol.h:12-20

  body 内若出现 0x7D(ESC) 则下一字节 XOR 0x20 还原
  body[1] = cmd, body[2..3] = pay_len(小端), body[8..] = payload,

// 命令码成对定义（请求 + ACK）

具备：帧同步头 + 转义（解决 payload 内含保留字节）+ 校验和 + 请求/应答配对 + 错误码 + 回调分发。

V307 侧则完全相反：phone_control.c:244-278 手写 4 状态解析器处理 0xFB+id+vH+vL，无校验、无帧头、无转义；采集包 14 字节也是硬编码 buf[14] = {0xFA, ...}。

为什么这对本项目重要 两条链路（USB AOA bulk 与串口）都靠"某几个字节恰好不会出现在数据里"来保证不歧义。 现在命令码只占 0x02~0x0D，能量值可能落在任意 16 位， 只因为能量包有 0xFE 前缀且长度固定 5，才没冲突。一旦要加"带 payload 的命令"（比如让 App 下发 App 包名），这套裸协议立刻失效。

运行时参数默认值Phone/mic_hum.c:24-29 全局变量初始化Config.h 宏 + mic_hum.c 引用，便于统一调参

4.5 异味构建包含靠"文件在不在"，不靠特性开关

obj/Phone/subdir.mk 无条件编译 17 个 .c：OLED.c、ads1115.c、aoa_host.c、ch32v30x_usbfs_device.c、diskio.c、ff.c、ffsystem.c、ffunicode.c、joystick.c、mic_hum.c、phone_control.c、sdio_sd.c、sdio_test.c、sw_udisk.c、usb_desc.c、usbhs_dev.c、message。

其中 ff.c(6982) + ffunicode.c(15593) = 22575 行，占 Phone/ 目录源码的 63%。而 TEST_MODE=0（正式吹气模式）一行都用不到。

目前的"排除手段"是把扩展名改成 .bak：usbhs_dev.c/h.bak、ch32v30x_usbfs_host.c.bak。原因是 MounRiver Studio 会重新生成 subdir.mk，手工编辑会被覆盖。

代价（不夸大） 由于 --gc-sections 开着，flash/RAM 没有被浪费（已实测：约 10% / 约 16%，随 TEST_MODE 变化）。 真正的代价是：编译时间（每次全量编译 2 万多行 FatFs）、警告噪音（-Wunused）、以及"改一个文件不知道会不会影响别的模式"的心理负担。

4.6 异味没有错误码/日志级别体系

V307 侧的错误传递是"printf 一句话 + 返回 int"，AOA_Err_t 是本项目里唯一的枚举错误码（aoa_host.h），sdio_sd.c 有 SD_Error，但两者不共享。

H417 侧有 CMD_ERR 统一错误码 + Voice_Protocol_SendError()。

更实际的问题是：正式的 TEST_MODE=0 构建里，printf 全量开启。没有 LOG_LEVEL / DEBUG_PRINTF 之类的编译开关——出货固件和调试固件在日志行为上完全一样。

5整体层问题（8 条）

本章是本次分析最重要的部分 前两章是"代码写得好不好"，本章是"配置和实物对不对得上"。后者会造成真实故障，而不是维护成本。

5.1 缺陷PB5 冲突：Config.h 说是 I2S3_SD，板子上是电源控制脚

代码侧证据链（事实）

// 1) Config.h:37  把 PB5 定义为 I2S3 的数据线
#define I2S3_SD_PIN_ENC        HAL_GPIO_PIN(1, 5)      // PB5

// 2) mic_hum.c:491  初始化时把它配成复用浮空输入
Hal_GPIO_Init(I2S3_SD_PIN_ENC, HAL_GPIO_MODE_AF_INPUT, HAL_GPIO_SPEED_VERY_HIGH, I2S3_GPIO_AF);
//    HAL_GPIO_MODE_AF_INPUT → GPIO_Mode_IN_FLOATING

// 3) main.c:53-57  更早的时候，同一个 PB5 被配成推挽输出并置高
GPIO_InitStructure.GPIO_Pin  = GPIO_Pin_5;
GPIO_InitStructure.GPIO_Mode = GPIO_Mode_Out_PP;
GPIO_Init(GPIOB, &GPIO_InitStructure);
GPIO_SetBits(GPIOB, GPIO_Pin_5);

原理图侧证据链（事实，来自 电路.txt 网表）

U15.91  name=PB5  net=PWR_CTRL

R12 (4.7kΩ):  pin1 → $1N2305       pin2 → PWR_CTRL
R11:          pin1 → GND           pin2 → $1N2305     // 基极下拉
Q3 (NPN):     1(Base) → $1N2305    2(E) → GND    3(C) → $1N1852
R10:          pin1 → 5V_IN         pin2 → $1N1852    // Q2 栅极上拉到源极
Q2 (P-MOS):   1(G) → $1N1852       2(S) → 5V_IN  3(D) → VPHONE

推导（推断）

PB5 状态Q3Q2 栅极Q2VPHONE（手机 VBUS）
输出高导通被拉低导通得电
浮空输入（AF_INPUT）截止（R11 下拉）被 R10 拉到 5V_IN截止断电

执行时序

main()
 └─ main.c:57           GPIO_SetBits(GPIOB, Pin_5)        // PB5 高 → 手机得电
 └─ main.c:298          Phone_Control_Init()
     └─ phone_control.c:163  Mic_Hum_Init()
         └─ mic_hum.c:491    Hal_GPIO_Init(PB5, AF_INPUT) // ← PB5 变浮空 → 手机关电
结论 在 TEST_MODE = 0（正式吹气模式）下，Mic_Hum_Init() 执行之后，给手机供电的 Q2 会被关断。 这不影响 TEST_MODE = 5（当前模式），因为那条路径不调用 Mic_Hum_Init，PB5 保持输出高。 推测这可能正是"想跑吹气模式却换来手机掉线/反复重连"这类现象的隐藏原因之一。 具体现象取决于手机是否自带电池、以及 VPHONE 断开时 Android 是否立即认为 USB 拔出。本条必须实测确认（见第 8 章第 1 项）。

5.2 缺陷Config.h 的整个 I2S 段在 V3 板上不成立

把 Config.h:19-43 声明的引脚逐个丢进网表核对：

引脚Config.h 声明原理图实际结论
PB12I2S2_WSU15.51，net 为空悬空
PB13I2S2_CKU15.52，net 为空悬空
PB15I2S2_SDU15.54 → U11.5（HC-05 模块）接到蓝牙 STATE 脚
PA15I2S3_WSU15.77，net 为空悬空
PB3I2S3_CKU15.89，net 为空悬空

也就是说：这份 电路.txt 对应的板子上没有 I2S 麦克风的接线，而 Config.h 却把它标为"板无关"并默认启用 BOARD_V3。

两种可能，需要你确认哪一种
  1. 电路.txt 是较新的 V3 改版，麦克风被移除了（改用 HC-05 语音模块？），但 Config.h 还留着 V1 时代的 I2S 段 → 配置过期。
  2. 电路.txt 导出不完整 / 不是我看到的那个板子 → 那 5.1 的 PB5 冲突也需要重新核对。
无论哪种，都说明代码里的"板级配置"和实物之间缺少一道核对机制。

5.3 异味板上一半器件在 Config.h 里没有名字

从网表里提取出的、有明确角色的器件，逐项比对 Config.h：

5.4 异味两路压差传感器读同一信号，Config.h 没表达取舍

网表里：传感器 → 运放 → 同时送 ADS1115（AIN0/AIN1，16 位）和 MCU 片内 ADC8/ADC9（12 位，即 PB0/PB1）。

Config.h:84-85 只定义了片内通道号：

#define PRESSURE_ADC1_CH   8
#define PRESSURE_ADC2_CH   9

没有任何地方说明"这两路信号同时也接到了 ADS1115 的 AIN0/AIN1"，也没有说明哪一路是权威读数。更新记录里 ADS1115 的注释是"AIN0=压差传感器2 AIN1=压差传感器1"，而 Config.h 的注释顺序相反（传感器1→ADC8、传感器2→ADC9）——两处命名不一致。

5.5 异味编译期模式 + 魔法数字，且模式代码散在 main.c

// mode.h 全文（核心部分）
#define TEST_MODE           5
/* 0=正常运行 1=SDIO测试 2=U盘 3=FAT读 4=USBHS枚举调试 5=HID键鼠 */

问题不在"用宏"，而在：

  • 0 是"正式功能"，却排在最后，且用 0 表示"正常"违反直觉（其他都是 1~5 的序号）。
  • 宏值被用在 5 个文件里做条件编译（main.c、usb_desc.c、ch32v30x_usbfs_device.c、usbhs_dev.c…），没有任何地方列出"这个宏会让哪些文件走哪条分支"。加一个模式需要改多处。
  • 正式模式的实现（Phone_Control_*）反而是最干净的一支，其它 5 个模式全是试验代码，却和正式代码共享一个宏命名空间。

5.6 异味文档与代码/实物不同步

文档说法实际来源
"SDIO 引脚 PD0(CD检测)"网表里卡座 CD → PC6；而 sdio_sd.c 只配了 PC8–PC12 + PD2，没有 CD更新记录一百零八 vs 电路.txt
"板载 LED"（我在上一轮导读里也这么写过）PB5 是 PWR_CTRL，PB8 才是 LED见第 9 章更正
Config.h 注释"压差传感器1→PB0/ADC8"更新记录写"传感器1→运放→PB0/ADC8"一致，但 ADS1115 侧编号相反两处注释

这不是"文档写得不好"，而是缺少单一的板级定义源：引脚同时存在于 Config.h、更新记录 txt、原理图 JSON、以及各类 .c 注释里，四份都能独立漂移。

5.7 异味业务层与硬件耦合，缺少可测试边界

phone_control.c:43-53 直接操作 USART 寄存器：

static void USART1_RX_Init(void) {
    GPIO_InitStructure.GPIO_Pin  = GPIO_Pin_10;
    GPIO_InitStructure.GPIO_Mode = GPIO_Mode_IN_FLOATING;
    GPIO_Init(GPIOA, &GPIO_InitStructure);
    USART1->CTLR1 |= USART_Mode_Rx;      // 绕过外设库直接改寄存器
}

业务层写"某个具体 UART 的某个具体引脚"，意味着换板子/换串口就要改业务代码。

更深的问题是：Mic_Hum_Poll、Phone_Control_Poll、AOA_Host_* 全都既做逻辑又碰硬件，没有任何一个函数可以在 PC 上跑单元测试。吹气状态机（mic_process，170 行）逻辑最复杂、最需要测试，却和 DMA 中断绑死。

5.8 异味缺少故障可观测性

V307 的调试输出全是 printf 无条件输出。当用户在现场说"吹气不灵"时，能拿到的信息只有串口日志——而串口是 2 Mbps 且与 CH340 共享，一旦 SW3 拨到 ESP8266 侧，串口就没了。

对比之下，H417 的 Serial_CtrlBlock 里有 TxDropCount——这是一个"日志系统自己丢了多少包"的计数，属于可观测性设计。

V307 侧目前没有任何计数器：不说丢了几个命令、不说 AOA 重连了几次、不说吹气误判了多少次。OLED 也只在 TEST_MODE=2 才显示调试状态。

6H417 侧同样存在的问题

为了公平——H417 那份也不是"标准答案"。以下问题同样成立：

6.1 异味Config.h 用 #ifdef __SERIAL_H 做隐式依赖

// Config.h:21 和 :82 两处
#ifdef __SERIAL_H
    ... 全部串口宏 ...
#endif /* __SERIAL_H */

设计意图：只有在包含了 Serial.h 之后，串口宏才可见，避免污染其它翻译单元。

但 __SERIAL_H 是 Serial.h 的 include guard —— 这是在依赖 include 顺序。Serial.c:1-2 恰好是 #include "Serial.h" 再 #include "Config.h"，所以能工作；换个顺序或换个文件就静默失效。

而且这制造了隐藏的循环依赖：Serial.h 不包含 Config.h，Config.h 又需要 Serial.h 先被包含 —— 只能靠约定维持。

6.2 异味BOARD_V1 / V2 两个块重复度过高

Config.h:19-73（V1）与 :80-132（V2）中，串口的 DMA_INSTANCE、TX/RX_DMA_CHANNEL、DMAMUX_CHANNEL、DMA_REQUEST、TC/TE_FLAG、IRQn、BUF_SIZE、RING_SIZE 完全相同（各 25 行 × 2 = 50 行纯重复），只有 4 个引脚不同。应抽出公共段。

6.3 缺陷Serial.c 的中断开关不保存原状态

// Serial.c:299-307
    __disable_irq();
    uint16_t used = Serial_TxUsedRaw(p);
    uint16_t free_bytes = (uint16_t)(p->TxRingSize - used - 1);
    if (len > free_bytes) {
        p->TxDropCount++;
        __enable_irq();            // ← 无条件开中断
        return 0;
    }
    ...
    __enable_irq();                // ← 无条件开中断

__disable_irq() / __enable_irq() 是"设置/清除 mstatus.MIE"的裸操作，不保存进入前的状态。若在 ISR 上下文里调用 Serial_SendArray_DMA，函数返回时会把中断意外打开。

严重性评估：理论风险，当前实际影响低 我 grep 了 H417 全部代码：Serial_Dbg_Printf / Serial_SendArray_DMA 目前只在非中断上下文被调用（Mic_Hum_Poll、初始化、测试循环）。 所以现在不会出问题。但这是颗定时炸弹——只要有人在某个 _IRQHandler 里加一行 Serial_Dbg_Printf 就会中招。 正确写法是 uint32_t saved = __get_MSTATUS(); ... __set_MSTATUS(saved); 或用一个 "critical section" 嵌套计数器。

6.4 异味hardware.c 的模式分支里 while(1) 不返回

// hardware.c:14-56
void Hardware(void) {
#if (SYSTEM_MODE == MODE_GPIO_TOGGLE)
    { ... while (1) { 翻转 GPIO } }        // 永不返回
#elif (SYSTEM_MODE == MODE_PHONE_CONTROL)
    Phone_Control_Init();
    while (1) { Phone_Control_Poll(); }    // 永不返回
#elif (SYSTEM_MODE == MODE_DUAL_MIC_TEST)
    Mic_Hum_TestLoop();                    // 阻塞死循环
#endif
}

名为 Hardware() 的"硬件初始化入口"，实际上承担了"主循环"的职责。名字与行为不符，且函数永远不返回，无法被组合。

6.5 异味双核条件编译让宏满天飞

hardware.c:8-12、:16、:52，Serial.c，以及 Config.h 的板型块，都参与 Core_V3F/Core_V5F 判定。加上 BOARD_V1/V2、SYSTEM_MODE，H417 侧的配置空间有 2(核) × 2(板) × 3(模式) = 12 种组合，而代码里没有任何地方声明"哪些组合是有效的"。

6.6 异味实例抽象被业务层绕过

见 2.4：mic_hum.c:389-492 里写死了 SPI2、SPI3、DMA2_Channel1、DMA2_Channel2、DMA_MuxChannel9/10、请求号 66/68、以及手工写的 SPI2->I2SPR = 0x00C3。

特别是 I2SPR = 0x00C3 这个魔数（mic_hum.c:458,462）：它直接覆盖 I2S_Init() 算出的分频值，注释里没有任何推导过程。

9更正：上一轮我说错的一处

更正内容 上一轮交付的《VOICE 代码导读手册》第 1 章我写了：
"板载 LED 在 PB5，不是 PB0。main.c:53-57 配的是 PB5。"
这是错的。main.c 在 :50-57 确实操作 PB5，但既没有注释说明是 LED，我也没有核对原理图就下了结论。
核对网表后：PB5 = PWR_CTRL（经 R12 → Q3 → Q2 控制手机供电），PB8 经 R52 才是 LED。
读者请注意以本文档为准。

这个错误本身也是个教训：main.c 里那 5 行代码没有任何注释，而它控制的是"要不要给手机供电"这种关键行为。按 P0 建议把它改成 Hal_GPIO_Set(PWR_CTRL_PIN_ENC) 并加注释，读代码的人就不会再猜错。
