0先定义什么算架构问题

不先把标尺定下来，讨论会滑向"代码风格"。 本文只用五个维度判断一件事是不是架构问题，凡是风格偏好一律不列。
边界依赖方向是否单向
有没有循环
契约同一事实是否只有一个定义源
漂移能否被发现
可测核心逻辑能否脱离硬件运行
可演进加一个功能要改几处
能否按需裁剪
可观测现场出故障能否定位

这五个维度里，契约类问题的危害远大于其它四类：其余四类最多让开发变慢，契约类会直接产生错误行为。所以下面按这个顺序排。

两个数字说明问题 MCU 侧 main.c 一个文件承担了三层职责； Android 侧两个文件占全部 5682 行的 65%（3711 行）。 其余文件都还健康 —— 说明架构问题集中在两个"上帝文件"上，而不是弥漫全项目。这是好消息：改动面是可控的。

Android 侧其实已经做过一轮架构重构 从 4ff40a0 那次提交看，已经抽出了 AppConstants / NodeHelper / GestureHelper / WechatCallController / AppAdapter 体系 （VoiceAccessibilityService 从 2249 行降到后来的规模）。 所以下面提的不是"从零做架构"，而是把那一轮没做完的部分补上。

2A 契约类问题（最危险）

A1 已漂移无障碍事件类型：XML 配置与代码期望不一致

res/xml/accessibility_service_config.xml:
    accessibilityEventTypes = typeViewClicked | typeWindowStateChanged | typeWindowContentChanged

VoiceAccessibilityService.java:132:
    if (event.getEventType() == AccessibilityEvent.TYPE_VIEW_SCROLLED) {
        lastScrollEventTime = System.currentTimeMillis();      // 期望收到滚动事件
    }

事实：accessibilityEventTypes 是系统侧过滤器，不在掩码里的事件类型根本不会投递。配置里没有 typeViewScrolled，所以第 132 行永远不会执行，lastScrollEventTime 只能由 waitForScrollIdle()（第 1963 行）自己初始化。

影响评估：功能仍可用，但"事件驱动"这个优化没有生效 checkScrollIdle()（第 1927 行）除了 300ms 时间门外，还有 posHash 两次读取比对作为兜底判据，所以滚动停止检测依然能工作，只是退化成"300ms + 100ms 轮询"。 真正的危害是认知漂移：更新记录第九十七轮把这件事记作"滑动停止检测改为事件驱动"，代码注释也这么写，而实际是轮询。后来人据此推理会得出错误结论。
二选一修掉：① 补上 typeViewScrolled 订阅（但要让 onAccessibilityEvent 的三个前置调用足够廉价，否则事件量激增会拖慢服务）；② 明确改注释与文档，承认它是轮询。 不要保留"文档说 A、代码是 B"的状态。

A2 已漂移包可见性：<queries> 与 KNOWN_APPS 不一致

来源包数量差异
AndroidManifest.xml 的 <queries>9queries 缺少：爱奇艺 com.qiyi.video、腾讯视频 com.tencent.qqlive、优酷 com.youku.phone、番茄 com.dragon.read、起点 com.qidian.QDReader
MainActivity 的 KNOWN_APPS14

而且同时声明了 QUERY_ALL_PACKAGES 权限 —— 与显式 <queries> 是两套重复手段，且会触发应用商店的政策审查。包可见性策略处于"没想清楚"的状态。

A3 已漂移协议常量在 6 处各写一份，且无版本协商

#位置内容
1mic_hum.h 的 HUM_CMD_* 枚举内部命令码
2phone_control.c:313-328 的映射 switch内部码 → AOA 字节
3phone_control.c:55-74 的串口菜单打印人读的对照表
4phone_control.c:9-40 的文件头注释又一份对照表
5MainActivity.java:56-67 的 CMD_*App 侧常量
6App 里各 handleDefaultCommand 的 case 标签实际使用点

没有版本协商：MCU 在 AOA 识别字符串里报了 AOA_VERSION "1.0"，但那是给系统看的；App 侧 versionName "1.0" 是给自己的。两者之间没有任何运行时的协议版本握手，一旦只刷了一边，故障现象是"命令乱执行"，而不是"明确报错"。

A4 已漂移板级引脚：代码 / 文档 / 原理图三处各一份

已在上一份报告详述（PB5 冲突、SD 卡检测 PC6 vs PD0）。这里只补一条结构性结论：

  • Config.h 只有 OLED 片选一处做了板型区分，其余标注"板无关"—— 但引脚接在哪本质上是板决定的
  • 缺失的板级事实：PWR_CTRL、LED、SD_CD、HC-05、ESP8266、CH340、模拟开关、以及"CTRL0/CTRL1 由机械开关控制、软件不可见"这条关键约束
  • 没有任何机制能在"代码与实物漂移"时报警

A5 已漂移编译期宏的影响面没有声明

TEST_MODE 出现在 5 个文件里做条件编译：main.c、usb_desc.c、ch32v30x_usbfs_device.c、usbhs_dev.c、mode.h。 没有任何地方列出"某个取值会让哪些文件走哪条分支"。加一个模式需要通读全工程搜索。

A6 构建包含靠文件扩展名，不靠特性开关

obj/Phone/subdir.mk 无条件编译 17 个 .c，含 ff.c(6982行) + ffunicode.c(15593行)
排除手段：把文件重命名成 .bak    ← usbhs_dev.c/h.bak、ch32v30x_usbfs_host.c.bak
原因：MounRiver Studio 会重新生成 subdir.mk，手工编辑会被覆盖
这一条我要说清楚危害边界，避免夸大 由于工程开启了 -ffunction-sections -fdata-sections -Wl,--gc-sections，未引用的代码与数据确实会被链接器丢弃 （我核对过 map，sdio_test.o 的两个 16 KB 缓冲区落在 "Discarded input sections" 里）。 实测占用约 FLASH 10% / RAM 16%（TEST_MODE=2 构建：.text 25100 B + .vector 444 B / 256 KB，.bss 8416 B + .data 320 B + 栈 2048 B / 64 KB），资源不是问题。
真正的代价是：编译时间（每次全量编 2 万多行 FatFs）、警告噪音、以及"某文件到底参与哪个构建"这件事没有任何声明可查。

注：这个数字随 TEST_MODE 变化（换模式后实测 .text 在 24~25 KB 之间浮动），引用时务必标注是哪次构建。

3B 边界类问题

B1 MCU：main.c 承担三层职责

305 行里，TEST_MODE 2 的 U 盘逻辑 46 行、TEST_MODE 3 的 FatFs 读取 84 行、TEST_MODE 5 的摇杆鼠标 66 行 —— 这些是完整的功能实现，不是初始化。对照 H417 版：main.c 只有 59 行，模式分发在 hardware.c 的 Hardware() 里。

B2 MCU：时钟使能 API 被拆在两个文件

API所在文件
GPIO_ClockEnable()Common/hal_gpio.c
SPI_ClockEnable() / DMA_ClockEnable() / AFIO_ClockEnable()Common/Config.c
这正是"忘记开时钟"那个坑的结构性根源 Hal_GPIO_Init() 不自动开时钟，而它无法顺手调用 SPI/DMA 的时钟函数 —— 因为那些函数在另一个文件里，而且没有任何统一入口。 所以只能靠每个调用点手写 5~10 行 ClockEnable（mic_hum.c:469-478 就是典型）。 把 API 收拢到一处，这类 bug 会整类消失。

B3 MCU：业务层直接操作芯片寄存器

// mic_hum.c:481   业务层直接读写 AFIO 寄存器来释放 JTAG
AFIO->PCFR1 = (AFIO->PCFR1 & ~AFIO_PCFR1_SWJ_CFG) | AFIO_PCFR1_SWJ_CFG_JTAGDISABLE;

// phone_control.c:52   业务层直接改 UART 寄存器
USART1->CTLR1 |= USART_Mode_Rx;

两处都应该是 HAL 函数。第二条更严重：它把业务层和"具体是哪个 UART、哪个引脚"绑死了。

B4 MCU：hal_gpio 无条件独占全部 EXTI 向量

hal_gpio.c:159-220 定义了 7 个处理函数（EXTI0..4 / EXTI9_5 / EXTI15_10）， 实测它们全部进入最终镜像（.vector 直接引用，gc-sections 收不掉），而全项目从未调用过 Hal_GPIO_IRQ_*。

危害不在 flash（几百字节），而在于：集成任何自带 EXTI 处理的第三方驱动都会重复符号链接失败；而走 HAL 的回调接口又丢失了上下文（回调签名 void(*)(void) 无参数）。

B5 Android：71 个 static、其中 54 个 public static —— 全局单例式架构

MainActivity 调用无障碍层的实际形态：
    VoiceAccessibilityService.focusNext();
    VoiceAccessibilityService.clickFocused();
    VoiceAccessibilityService.getForegroundPkg();
    VoiceAccessibilityService.isBiliFullscreen();
    WechatIds.isChatItem(viewId);
    ...

模块之间不是通过接口交互，而是通过全局静态方法。后果：

  • 无法替换实现（想给 focusNext 写个假实现做测试，做不到）
  • 依赖关系不可见 —— 看 MainActivity 的构造函数完全不知道它依赖无障碍层
  • 静态可变状态（wechatNavMode、showMarkerEnabled、sCollectedEvents）跨 Activity 存活，生命周期难以推理

B6 Android：SharedPreferences 键名跨文件硬编码

MainActivity.java:1148-1151              VoiceAccessibilityService.java:1569-1572
prefs.getInt("calib_top_" + curPkg, ...)  sp.getInt("calib_top_" + pkg, ...)
prefs.getInt("calib_bot_" + curPkg, ...)  sp.getInt("calib_bot_" + pkg, ...)
prefs.getInt("calib_centerTop_" ...)      sp.getInt("calib_centerTop_" ...)
prefs.getInt("calib_centerBot_" ...)      sp.getInt("calib_centerBot_" ...)

写入方和读取方各自拼接同一套键名。任何一方改名（哪怕只改一个字母）都会静默失配 —— 校准线的表现会变成"调了没用"，而不会有任何报错。 键名同时还有 voice_ctrl 与 wechat_ids 两个不同的 prefs 文件、以及 app_* 系列的拼接式键，全项目共 20 余种键名散落在 4 个文件里。

B7 Android：两个 AccessibilityService 同时注册，原因无记录

<service android:name=".VoiceAccessibilityService" ... />
<service android:name="com.google.android.accessibility.selecttospeak.SelectToSpeakService"
         android:exported="true">
    <intent-filter android:priority="10000"> ... </intent-filter>
</service>

第二个服务是个空实现（SelectToSpeakService.java 33 行），存在的理由是"绕过微信节点混淆"。 但从清单里看不出任何原因，且它 exported="true" + 优先级 10000 —— 一个架构上的非常规手段，却没有任何注释解释为什么需要它、什么时候可以移除。

4C 可测类问题

C1 MCU：全项目零测试，且最复杂的逻辑被钉在硬件上

mic_process（170 行，5 状态机 + 3 层组合判定）是全项目最需要测试的代码，但它和 DMA 中断、全局变量绑在一起，在 PC 上跑不起来。

而它其实完全可以测 —— 输入是一个 (blowing, energy) 序列，输出是命令序列，没有任何硬件依赖。这是"零成本可获得的最高收益"。

C2 Android：app/src/test 目录根本不存在

app/build.gradle 里声明了：
    testImplementation 'junit:junit:4.+'
    androidTestImplementation 'androidx.test.ext:junit:1.1.2'
    androidTestImplementation 'androidx.test.espresso:espresso-core:3.3.0'

实际目录：
    app/src/main          ← 只有这个
    （没有 app/src/test，也没有 app/src/androidTest）

依赖声明了但从未使用。而项目里有大量不需要设备就能测的纯逻辑：

可测的纯逻辑为什么能脱离设备测
UsbAccessoryManager.readLoop 的三态解析输入是字节流，输出是回调序列 —— 抽成 FrameDecoder 类即可纯测
avgNoExtremes（去极端平均）纯函数
Calibration 的键名生成纯字符串逻辑（也可反过来验证 B6 的失配）
WechatIds 的匹配规则纯字符串逻辑
<queries> vs KNOWN_APPS 一致性读 XML + 读常量比对，能在 JVM 单测里跑

C3 MCU：没有宿主端构建路径

全部代码只能用 MounRiver 的 riscv 工具链编译。mic_process 这类没有硬件依赖的代码，也应该能用宿主 gcc 编译并跑测试。

5D 可演进类问题

D1 mode.h 用单个魔法数字表达 6 种编译配置

#define TEST_MODE           5
/* 0=正常运行 1=SDIO测试 2=U盘 3=FAT读 4=USBHS枚举调试 5=HID键鼠 */

问题不在"用宏"，在于：0 表示"正式功能"却排在最后；6 种配置互斥，无法表达"要 AOA + 也要 HID"这种组合；宏值散落 5 个文件。

D2 MCU：没有串口抽象层

能力H417 版 Serial.c（452 行）V307 现状
结构控制块 + 双实例表，配置数据驱动无
RXDMA + 空闲中断自动分帧，双缓冲phone_control.c:199 主循环轮询，一次 1 字节
TXDMA 环形缓冲 + 溢出计数debug.c 阻塞 printf
中断组织USART_IRQ_Handler(port) 单函数多实例无（靠轮询）
这个差距有实际后果 mic_hum.c 在每 8ms 的 tick 上可能打印，Mic_Hum_TestLoop 更是每 tick 一行。 2 Mbps 下打印 60 字节约 0.3ms，而这是阻塞的 —— 会直接挤压主循环节奏，影响命令响应时延。

D3 MCU：没有帧协议层

H417 侧有完整的 voice_protocol（AA55 帧头 + 0x7D 转义 + checksum16 + 请求/应答配对 + 错误码 + 回调分发）； V307 侧靠"某几个字节恰好不会出现在数据里"来保证不歧义（phone_control.c:244-278 手写 4 状态解析器，无校验、无转义）。一旦要传带载荷的命令（比如让 App 下发包名），这套裸协议立刻失效。

D4 Android：两个上帝类

VoiceAccessibilityService 一个类里塞了 9 件事：事件入口 / 页面判定 / 节点收集 / 焦点导航 / 滚动算法 / 红框绘制 / 学习模式 / 微信通话 / 手势模拟。
MainActivity 塞了 7 件事：视图绑定 / 应用扫描 / SELECT-CONTROL 状态机 / 命令分发 / 校准 UI / 悬浮窗 / 学习流程。
上一轮重构已经把 适配器 和 微信通话 抽出去了，剩下的这些还没抽。

D5 没有"板型能力声明"

现在判断"这块板有什么"只能靠 #ifdef BOARD_V3 逐个外设判断。缺少一张"板 → 能力"的对照表，导致：

  • 加一块新板要通读 Config.h 才能知道要定义哪些宏
  • 无法在编译期发现"代码用了这块板没有的外设"
  • H417 侧的配置空间是 2(核) × 2(板) × 3(模式) = 12 种组合，而代码里没有任何地方声明哪些组合是有效的

6E 可观测类问题

E1 没有任何运行时计数器

用户在现场说"吹气不灵"，能拿到的只有串口日志。而这些问题都无法回答：

问题需要的计数器（现在都没有）
命令丢了吗？丢了几条？s_cmd_queue 满时丢弃计数（mic_hum.c:80 静默 return）
AOA 断连重连过几次？重连次数、失败次数
传感链路重启过吗？全零重启次数（现在只有 printf）
采集模式超时过吗？采集超时计数

E2 打印无级别，出货固件与调试固件行为相同

// micro: 没有 LOG_LEVEL / DEBUG_PRINTF 之类的编译开关
// 正式 TEST_MODE=0 构建里 printf 全量开启

E3 排障时可能压根没有日志通道

串口 USART1 经模拟开关 U4 在 CH340 / ESP8266 / MCU 三者间切换，而控制脚 CTRL0 由一个机械拨动开关 SW3 驱动 —— 软件看不到开关状态。 如果现场开关被拨到 ESP8266 一侧，整个串口日志通道消失，且现场无法判断原因。

7MCU 目标文件树

设计原则：基础设施按层分，业务按模块分，试验按类型分。依赖方向严格单向：Board → Hal → Drivers → Sense → App → User。

Common/ → Board/ + Hal/，把"板级事实"和"硬件抽象"分开。

9五个关键机制

机制 1 · 单一真源 + 生成器

tools/protocol.json                        ← 唯一手写的地方
{
  "version": 2,
  "commands": [
    {"name": "ENTER",  "value": "0x02"},
    {"name": "BACK",   "value": "0x03"},
    ...
  ],
  "params": [ {"id": 0, "name": "TH_HIGH"}, ... ],
  "packets": [ {"head": "0xFE", "len": 5, "name": "ENERGY"}, ... ]
}
        │  gen_protocol.py
        ├──→  VOICE_V307/App/protocol.h          （C 枚举 + 映射表）
        └──→  voice_control/.../core/Protocol.java（Java 常量）
             并同时生成 PROTO_VERSION，MCU 在 AOA 识别字符串里带上、App 启动时比对

收益：加一个命令从"改 6 处"变成"改 1 处 + 跑一次生成器"；且版本号让"只刷了单边"这种情况从乱执行变成明确报错。

机制 2 · 板级定义单一真源 + 自动核对

tools/check_board.py
读 电路.txt（嘉立创 EDA JSON）的网表  →  与 Board/board.h 的宏逐脚比对
输出三类结论：
  ① 宏指向的引脚在网表里是否存在、连到了什么
  ② 网表里有、board.h 没定义的重要器件（如 HC-05 / ESP8266 / PWR_CTRL）
  ③ 同一引脚在 board.h 里被两个外设占用（如 PB5 的 I2S3_SD 与 PWR_CTRL）

这个脚本我已经用一次性代码跑过一遍（就是前两份报告里那些表），脚本化之后每次改板子跑一次即可。这是唯一能让"代码与实物"不再漂移的手段。

机制 3 · 特性开关替代编译模式

/* App/app_config.h —— 可组合，不再是互斥的数字 */
#define FEAT_SENSE_PRESSURE  1
#define FEAT_SENSE_MIC       0
#define FEAT_USB_AOA         1
#define FEAT_UDISK           0
#define FEAT_HID_MOUSE       0
#define FEAT_SD_BENCH        0

/* 每个 .c 文件体整体用开关包住 */
#include "app_config.h"
#if FEAT_UDISK
... 全部 U 盘模式代码 ...
#endif

/* obj/makefile 用 ifeq 决定加入哪些 .o，不再靠改 .bak */
ifeq ($(FEAT_FATFS),1)
OBJS += ./Drivers/ff.o ./Drivers/diskio.o
endif

三个收益：不再需要 .bak 排除法；编译时间随特性裁剪；"某文件属于哪个构建"从"靠搜索"变成"看开关"。

机制 4 · 把隐式契约变成可校验的断言

契约校验手段成本
引脚宏与实物一致check_board.py（机制 2）半天写脚本
协议两边一致protocol.json 生成 + 版本号比对半天写生成器
MCU 启动时外设真的在Board_Check()：读 ADS1115 应答 / OLED 初始化 / USB 枚举，失败在 OLED 显示错误码半天
Android 订阅的事件类型覆盖代码所需A11yService.onServiceConnected() 里读 getServiceInfo().eventTypes，与代码期望的掩码比对，不匹配就 Toast（这是运行时能读到的）1 小时
<queries> 与 KNOWN_APPS 一致JVM 单测：读 XML + 读常量比对（不需要设备）1 小时
构造合法性Hal_GPIO_Init 加 pin > 15 / port >= NUM_PORTS 断言10 分钟

机制 5 · 让核心逻辑脱离硬件

MCU：手势状态机宿主单测
Sense/gesture.c 输入是 (zone, value) 序列，输出是命令序列，零硬件依赖。
用宿主 gcc 编一个 test_gesture.c：注入"吹 20 tick 停 10 tick"，断言输出 short； 注入"吹 100 tick"，断言连续输出 hold。
这是全项目收益最高的一次测试投入。
Android：先建 4 个 JVM 单测
① FrameDecoder 的字节流解析（含跨包、半包）
② <queries> 与 KNOWN_APPS 一致性
③ Calibration 键名生成（反证 B6）
④ WechatIds 匹配规则
都不需要设备，./gradlew test 就能跑。

10迁移批次

批次顺序按风险排，不按重要性排：先做无行为变更的，建立安全网之后再做有行为变更的。

12不做清单

不做原因
不引入 RTOS当前是单循环 + 中断，把 DMA/I2C 全改成阻塞式后时序需求没有超出超级循环的能力。引入 RTOS 会让"为什么这么写"的原因全部需要重学，收益不成正比
不在 MCU 侧引入 C++ / 模板嵌入式这边 -Os + 手工内存管理的风格是稳定的，语言切换的收益是"更好看"，成本是整个工具链和习惯
不为了架构而重写 AOA / USB 层那部分刚刚稳定（坑 1~5 是反复实测才收敛的），重写的风险远大于收益
不给 Android 引入 MVVM / Hilt / Room这个 App 只有一个 Activity、一个 Service，数据量极小。引入框架的收益是"符合教科书"，成本是构建时间、学习成本和排障难度。只需要 ConfigStore 收拢配置就够
不把 WechatIds 的自动提取改成离线工具它的运行时提取虽然复杂，但正是应对微信版本变化的必要手段。要改的是"加注释说明为什么复杂"，而不是推翻
不在同一次改动里既重构又加功能批次 1~5 都是等价重构，夹杂新功能会让"回归"无法区分是重构引入的还是新功能引入的
一句话总结 这个项目的架构问题不是弥漫性的，而是集中在"契约没有单一真源"和"两个上帝文件"两点上。 所以最优路径是：先花 0.5 天建立测试安全网（顺带把 A1/A2 两条契约漂移暴露出来），再花 4.5 天做纯等价的结构搬迁，最后才动需要真机验证的部分。 其中批次 4（把状态机从硬件里剥出来加单测）建议排在任何传感层改动之前 —— 它是后面所有改动的保险。
本文档为架构方案，未修改任何工程文件。所有问题均附实际文件与行号证据； "资源占用"类结论均已核对链接器 map，未使用静态推断。凡标注"需实测"的部分需在真机上验证。
