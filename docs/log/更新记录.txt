一百一十二、Windows格式化失败根因: DMA模式死锁
----------------------------------------

现象: U盘识别但提示需要格式化，且Windows无法
完成格式化。

根因: main.c SD_Init后执行NVIC_DisableIRQ(SDIO_IRQn)，
但SD卡仍处于DMA模式:
- 读路径: SD_ReadBlock只等DMA硬件标志
  (DMA2->INTFR & 0X2000，无需中断) → 读成功
- 写路径: SD_WriteBlock(DMA模式)死等TransferEnd
  标志，该标志由SDIO_IRQHandler置位，但SDIO
  中断已被禁用且与USBFS同为优先级0无法嵌套
  → 死等SDIO_DATATIMEOUT(约30秒) → WRITE10
  超时失败 → 格式化失败

提示需要格式化本身正常: SD卡是空卡无FAT分区表。

修复:
1. main.c: SD_Init后调SD_SetDeviceMode(SD_POLLING_MODE)
   POLLING模式读写完全不依赖中断，USB中断里
   同步执行，无死锁风险(每扇区写约5ms够用)
2. sw_udisk.c: 补上读写失败SCSI错误上报
   读失败sense=0x03/0x11，写失败sense=0x03/0x03，
   CSW status=1让Windows重试

编译通过(text=23152)。烧录验证: Windows成功格式化，
写入123.txt正常(用户实测)。

- 无USBFS时钟冲突

- NVIC中断在触发(R>0证明)

分析: 高速握手失败后PHY降级到全速，但全速下主机仍
不发SETUP。可能是USBHS PHY在Device模式下信号质量问题，
或Type-A转Type-C线信号质量差。

   第三十轮更新 (2026-09-01)

=================================

----------------------------------------
一百零七、UsbAccessoryManager.start()可重入+isRunning()
----------------------------------------

问题: AOA断连后onDisconnected调用stop()，但start()中
readThread无条件new+start，如果重复调用start()会创建
多个读线程。BroadcastReceiver重复注册也会崩溃。

解决:
1. start()开头先unregisterReceiver(try-catch防首次未注册)
2. readThread改为可重入: if(readThread==null||!isAlive)
   才创建新线程
3. 新增isRunning()方法返回running标志，供外部查询状态

意义: start()可安全重复调用，不会创建多线程或注册崩溃。
必要性: 断连重连场景下start()可能被多次调用。

----------------------------------------
一百零八、断连时finish()让系统重新拉起App自动授权
----------------------------------------

问题: AOA断连重连后App还在运行，系统只发ATTACHED广播
不重新启动App，不触发intent-filter自动授权，弹USB权限
对话框。高位截瘫患者无法点击。

解决:
1. MainActivity.onDisconnected中调用usbManager.stop()+
   finish()：断连时让Activity自己销毁
2. onCreate中复用sUsbManager时，如果!isRunning()则start()：
   App被系统重新拉起时确保USB启动

思路: 断连→App finish()→重连时App不在运行→系统通过
intent-filter重新拉起App+自动授权→不弹窗

状态: 用户反馈"方案一还是不行"，但代码保留待进一步验证。
可能原因: finish()后App进程未完全退出（无障碍服务保活），
系统认为App还在运行，不重新拉起。

意义: 尝试通过finish()让系统重新拉起App绕过权限对话框。
必要性: 高位截瘫患者无法手动点击USB权限对话框。

----------------------------------------
一百零六、scrollToVisible巨长卡片cardTooTall分软件处理
----------------------------------------

问题: B站有些视频卡片（带大图推荐卡）高度>1264px
(botLine-topLine=1504-240)，中心在中心区[600,1000]内，
但卡片顶部<topLine或底部>botLine，没完整出现在边界内。
scrollToVisible的cardTooTall&&inCenter条件直接不滑动，
红框被showHighlightClipped裁剪到边界内只显示部分，
用户看到"红框不截全也不滑动"。

根因: cardTooTall&&inCenter条件是第二十轮为朋友圈巨长卡片
(1487px占满屏幕，top=0和top=11之间振荡50px)设计的防振荡
措施。但B站大卡片也命中此条件，中心在中心区但卡片超出边界
时不滑动，红框被裁剪。该条件不区分软件，对B站误判。

解决: cardTooTall&&inCenter条件改为分软件处理:
- 微信/朋友圈: 保持原逻辑，巨长卡片中心在中心区就不滑动
  （防振荡，朋友圈卡片占满屏幕滑动无用）
- B站等: 巨长卡片中心在中心区时，检查中心是否已对齐到
  targetCenter:
  - abs(offset) < avgCardHeight/3 (≈142px) → 中心已对齐，
    不滑动（卡片太高无法完整显示，中心对齐即可接受）
  - abs(offset) >= avgCardHeight/3 → 中心偏离较多，
    继续滑动对齐到targetCenter

同时把isWechat声明从条件3前移到条件1前，供条件1使用。

意义: B站巨长卡片中心偏离targetCenter较多时会滑动对齐，
对齐后才停止；不再像之前那样中心在中心区边缘就不滑动。
朋友圈保持防振荡不受影响。
必要性: cardTooTall条件本是为朋友圈防振荡设计，B站卡片
布局不同（标准RecyclerView线性滑动），不应套用同一逻辑。

踩坑: B站大卡片如果中心已对齐(offset≈0)时滑动50px(最小
moveDist)会偏离，然后又滑回来可能振荡。加abs(offset)
<avgCardHeight/3判断避免此情况：中心已对齐就不滑动。

   AOA断连重连优化 + Android端USB连接持久化
=================================

----------------------------------------
一百零一、AOA_Enumerate非标准PID判定（MCU端）
----------------------------------------

问题: 手机VID=0x2D95 PID=0x6013(非标准AOA VID/PID), 有class=0xFF接口
(3个端点: 2 bulk + 1 interrupt, 标准AOA只有2 bulk无interrupt)。
GET_PROTOCOL返回2说明支持AOA但未进入AOA模式, class=0xFF接口是ADB不是AOA。
之前直接把有class=0xFF+bulk端点的非标准PID设备判定为AOA,
导致MCU认为连上了但手机App显示"USB未连接"(数据被丢弃)。

解决: 在AOA_Enumerate中, 当PID非标准但找到bulk端点时, 用GET_PROTOCOL区分:
- GET_PROTOCOL返回>0(AOA_CheckSupport返回0) → 支持AOA但不在AOA模式
  is_aoa_device保持0, 让调用者发START切换
- GET_PROTOCOL失败/返回0(AOA_CheckSupport返回非0) → 可能已在AOA模式
  is_aoa_device=1, 直接使用class=0xFF接口

踩坑: AOA_CheckSupport返回值含义容易混淆:
- 返回0 = 支持AOA(GET_PROTOCOL>0, 未进入AOA模式)
- 返回非0 = 不支持或已在AOA模式(GET_PROTOCOL=0或失败)

意义: MCU不再误判非AOA设备为AOA设备, 避免无效通信。
必要性: 手机ADB接口和AOA接口都是class=0xFF, 必须用GET_PROTOCOL区分。

----------------------------------------
一百零二、AOA_Host_Connect强制USB Host重置（MCU端）
----------------------------------------

问题: 第一次连接成功(发START后100ms设备断开→重枚举为0x18D1/0x2D01)。
断连后重连时, 发START后设备5秒都没断开, 手机不响应START_ACCESSORY。
原因: App还在运行, Android的AOA框架状态不一致, 不重新切换到AOA模式。

解决: 在AOA_Host_Connect开头, 不再只做端口复位, 而是完整禁用USB Host 500ms
再重新启用(USBHS_Host_Init(DISABLE)→Delay→USBHS_Host_Init(ENABLE)):
- 禁用时D+/D-拉低 → Android检测到USB断开 → 清理AOA框架状态
- 重新启用后D+/D-恢复 → Android检测到USB插入 → AOA框架重置
- 再发START_ACCESSORY → Android响应 → 切换到AOA模式

意义: 每次连接前强制Android检测到USB断开-重连, 清理AOA框架状态。
必要性: 不强制断开, Android不响应第二次START, 导致重连失败。

----------------------------------------
一百零三、Android端USB连接持久化（UsbAccessoryManager + MainActivity）
----------------------------------------

问题: USB断连时Activity被销毁→onDestroy调用usbManager.stop()→BroadcastReceiver注销。
之后USB重插时App不在运行→系统弹"要打开声音控制来处理1.0吗？"对话框→需手动点击。

解决: 
1. UsbAccessoryManager:
   - callback和context改成volatile非final
   - 添加setCallback(Context ctx, Callback cb)方法, ctx非null时更新context
   - 所有callback调用前加if(callback!=null)检查
   - 保存ParcelFileDescriptor引用, closeStream()中显式关闭pfd

2. MainActivity:
   - sUsbManager改成static, onCreate中复用已有实例只setCallback(this,this)
   - onDestroy中只setCallback(null,null), 不调用stop()
   - onConnected()加try-catch防崩溃

意义: Activity被销毁后UsbAccessoryManager仍运行, BroadcastReceiver仍注册,
USB重插时ATTACHED广播直接处理, 不弹系统对话框。
必要性: 高位截瘫患者无法频繁找人点击对话框。

踩坑: 
- context用getApplicationContext()导致App闪退, 改回传入的context
- setCallback(null,null)会把context置null导致bringActivityToFront崩溃,
  改为只在ctx非null时更新context
- 删除intent-filter后App无法获取USB权限, 已恢复intent-filter

一百零四、accessory_filter.xml model修正
----------------------------------------

问题: accessory_filter.xml中model是CH32H417(旧H417板子),
但MCU端AOA_MODEL是CH32V307。intent-filter不匹配→系统不自动授权→弹对话框。

意义: intent-filter匹配后系统自动授权, 减少对话框。

一百零五、对项目的新理解
----------------------------------------

1. Android AOA框架状态问题: 第一次连接时Android检测到新USB设备插入,
   AOA框架是干净的, 响应START_ACCESSORY。断连后App还在运行,
   AOA框架状态不一致, 不响应第二次START。必须在MCU端强制USB断开-重连
   来清理Android的AOA框架状态。

2. USB Accessory权限模型: 
   - 有intent-filter → 系统弹"打开App"对话框 → 用户确认 → 权限授予
   - 无intent-filter → 需手动requestPermission() → 弹权限对话框
   - 已授权 → openAccessory()直接成功 → 不弹对话框
   - 权限是持久的, 一旦授权, 同一accessory不再弹对话框

3. static UsbAccessoryManager的边界条件:
   - App进程被杀死: static变量重置为null, onCreate创建新实例
   - App进程保活(无障碍服务): static变量保留, onCreate只setCallback
   - context指向已销毁Activity: getPackageName/startActivity仍可用
   - callback为null: 所有回调前加null检查, 不崩溃

4. 遗留问题: 断连重连时仍可能弹系统对话框, 需要用户点击一次"确定"。
   Android安全模型要求第一次必须人工授权, 之后权限持久化。
   对于高位截瘫患者, 需要有人帮忙做第一次设置, 之后自动。
   完全零点击方案可能需要root权限或系统签名, 暂未实现。

二、MCU端改动 (aoa_host.c / phone_control.c)
----------------------------------------

【坑1: 强制端口复位打断AOA切换】

现象: START_ACCESSORY发送成功(err=0)，但手机重新枚举为Mass Storage
      (class=0x08 sub=0x06)而不是AOA设备(class=0xFF)

根因: START_ACCESSORY后立即强制USB端口复位(PORT_CTRL reset)，
      打断了手机的AOA模式切换过程。手机收到总线reset信号后
      回到默认USB模式(Mass Storage)而不是AOA模式。

解决: 去掉START_ACCESSORY后的强制端口复位，改为:
      1. 等待手机自然断开(最多5秒)
      2. 如果手机自然断开 → 等待AOA重枚举
      3. 如果5秒没断开 → 硬端口复位作为兜底
      4. 超时后也硬端口复位清除死锁状态

关键日志对比:
  修复前: START_ACCESSORY → 强制reset → VID=0x2D95 PID=0x6011 (Mass Storage)
  修复后: START_ACCESSORY → 自然断开100ms → VID=0x18D1 PID=0x2D01 (AOA!)

----------------------------------------

【坑2: is_aoa_device枚举重试不重置】

现象: 重连时枚举到非AOA设备(VID=0x2D95 PID=0x6011 Mass Storage)，
      但代码误判为AOA设备，打印"AOA Mode Ready!"

根因: AOA_Enumerate()中 *is_aoa_device=0 在 ENUM_RETRY 标签之前。
      第一次枚举尝试发现AOA设备(VID=0x18D1)设置了 *is_aoa_device=1，
      但枚举失败后 goto ENUM_RETRY 重试，此时 *is_aoa_device 仍为1。
      第三次重试枚举到非AOA设备，但 *is_aoa_device 没有被重置为0。

解决: 将 *is_aoa_device=0 移到 ENUM_RETRY 标签之后，每次重试都重置。

----------------------------------------

【坑3: 软复位(开关SOF)无效】

现象: 手机不自然断开时，尝试软复位(禁用SOF→延时→启用SOF)，
      但PORT卡在0x00000001(bit0=连接, bit1=未使能)，30秒超时

根因: 软复位只是开关SOF生成，不产生USB总线reset信号。
      手机完全无感知，不会重新枚举。PORT死锁在连接但未使能状态。

解决: 用硬端口复位(PORT_CTRL reset)代替软复位。
      硬复位产生USB总线reset信号，强制手机重新枚举。
      同时超时后也硬端口复位清除死锁。

----------------------------------------

【坑4: keepalive导致循环断连】★最关键的坑

现象: AOA连接成功后，端口在5秒内持续掉线，反复重连，手机重复弹窗

根因: 添加了keepalive机制(每秒发0x00字节保活)，但在App还没打开
      USB accessory时，bulk OUT端点未就绪，TX失败(error 42)。
      3次重试失败后代码强制设 s_aoa_state=DISCONNECTED →
      触发自动重连 → 重连过程端口复位 → 再次连接 →
      App还没打开 → keepalive又失败 → 循环

关键: 用户指出"加入自动重连之前连接是稳定的，能发命令"，
      说明连接本身没问题，是keepalive+TX失败断连导致的循环。

解决:
  1. 完全删除keepalive机制(不需要，连接本身是稳定的)
  2. AOA_Host_Send()中TX失败3次后只返回错误码，
     不设 s_aoa_state=DISCONNECTED (TX失败≠断线)
  3. 恢复简单等待: AOA就绪后等3秒让App打开accessory
  4. 只有端口物理断开(port enable bit清零持续150ms)才触发重连

----------------------------------------

【坑5: 端口掉线检测过于敏感】

现象: USB信号短暂波动导致port enable bit瞬间清零，误判为断线

解决: AOA_Host_Poll()加三级防抖:
      检测到port disable → 等50ms再查 → 等100ms再查 → 三次都disable才断连

【最终AOA连接流程】

1. MCU初始化USB Host，等待手机插入
2. 手机以普通模式连接 (VID=0x2D95 PID=0x6013)
3. 发GET_PROTOCOL → 手机返回2(支持AOA)
4. 发SEND_STRING(厂商/型号/版本/描述)
5. 发START_ACCESSORY
6. 等待手机自然断开(5秒超时)
   - 断开 → 等待AOA重枚举
   - 没断开 → 硬端口复位 → 等待重枚举
7. 等待AOA重枚举(30秒超时)
   - AOA设备(VID=0x18D1) → 成功
   - 非AOA但支持AOA → 重新发START_ACCESSORY
   - 超时 → 硬端口复位 → 从头重试
8. AOA就绪，等3秒让App打开accessory
9. 进入命令循环，等待串口命令转发

【自动重连策略】
- 端口物理断开(防抖150ms) → 5秒冷却 → 自动重连
- 重连失败 → 3秒后重试
- TX失败 → 只返回错误，不断连
- 重连时如手机已在AOA模式 → 直接使用，不重新协商

一百二十、硬件I2C2修复成功(ACK时序后移) —— 三轮实测闭环

背景: 硬件 I2C2 版此前"脱机全 0"(A/B 确认硬件路径问题)。加 DEBUG

- 第1轮: 612 次失败全部 @130 = 读事务第 2 字节 RXNE 超时;

验证(用户复测): 0 次失败(前两轮 612+365);
ch1 16~14486 全量程(吹吸都测)、ch0 空闲、摇杆噪声 ±5 计数 ——
数据质量与软件版完全一致, 硬件 I2C2 转正。

踩坑:
- 多行文件编辑用 python -c 双引号传串, bash 转义会让多行替换

----------------------------------------
一百三十、波形卡顿真凶闭环(Java CRC 符号扩展)+主循环时序重构(TIM2)+UART7 迁移实验+EEG 医生端联调
----------------------------------------

背景: WiFi 调参链路的波形显示"单吹按住卡死/双吹正常", 历经三日
多轮排查(波特率/U4模拟开关/ESP固件/App渲染/NVIC优先级), 最终由
码道定位真凶——Java 有符号字节 CRC 污染。本章归档全部实验与结论。

★ 根因(码道定位, EspLink.java feedByte case 3):
  rCrc ^= b —— Java byte 有符号, payload 字节 ≥0x80 时 b 符号扩展
  成 0xFFFFFFxx, 异或污染 rCrc 高 24 位 → CRC 恒错 → 帧全丢。
  触发区间: s1_lo≥0x80 ⟺ s1∈[384,511](吹气饱和 500=0x01F4 必中)
  = "380-500 区间卡死"; 静息字节全 <0x80 = 正常。修复: rCrc ^= (b & 0xFF)。
  ★ 同源佐证: EEG 医生端 checksum16 有 &0xFF 故流畅——线索在手未追, 教训记录。

★ 主循环时序重构(码道, User/test_modes.c + esp_link 拆分):
  原结构: Delay_Ms(50) 固定拍 + 回主页冲角段 while(Busy) Delay_Us(100)
  忙等 + 传感器/波形/HID/诊断全挤一循环 → 圈耗时波动拖乱波形帧节奏。
  新结构: TIM2 自由运行(100µs/计数)实测圈耗时(loop=%lums 诊断);
  ①传感器+波形帧独立 50ms 计时(不依赖 USB 枚举——脱机也发) ②HID
  报告非阻塞节流(hid_elapsed>=need_ms, 去 Delay 与忙等) ③EspLink_Poll()
  只做 RX(参数下行), 波形发送拆 EspLink_SendWave(p1,p2) 独立调用
  ④esp_send_frame TXE 等待加 1ms 超时(ESP 端异常不再卡死主循环,
  diag 增 tmo 计数) ⑤未枚举 200ms 节流。

★ ESP8266 端(esp8266_link.ino):
  ESP_DEBUG 编译开关([WIFI] 调试行, 正式接 MCU 数据线时置 0——
  调试行混入 UART7 RX 通道); 保留 EEG 架构(TCP client/EEPROM 档案/
  PING 拦截/非阻塞写/关省电)。

★ 波形页(WaveView): 重写为 EEG WaveformView 同款(单通道×2 上下并排,
  niceNum 刻度/X 秒窗/Y 每格 Pa 可填写/暂停/清屏); 阈值虚线随参数联动。

★ 实验与结论(证据链全在 com9 日志/logcat 探针/原理图):
  ①U4 模拟开关路径(UART6/PC0/PC1)在 2M 下信号完整性劣化(RON×寄生
    电容 RC 低通)——UART7 排针直连(PE12/PE13, FullRemap)实验流畅;
    机械开关没事的原因: 触点 RON≈0 无寄生电容; 带宽 500MHz 无关。
  ②esp_link.c 硬件路径已迁移 UART7(H3 排针直连 ESP), U4 通道 3/4 退役。
  ③43% 帧损坏实测与 CRC bug 模型吻合——传输层无罪(字节到达正常)。
  ④医生端无波形根因: VOICE 配置 App 占用 41002(EADDRINUSE)——
    两 App 同端口冲突; 且医生端 tcpServer.start() 在波形页才启动。
  ⑤TEST_MODE 6(VOICE 三角波)/7(EEG 八通道 250Hz 仿真)已实现,
    排查利器保留。
  ⑥Pressure_ReadPaRaw(不钳位)新增——波形可显示饱和段真实动态;
    手势判定仍用钳位 ReadPa 不变。

★ 诊断: 串口1 每拍(20Hz)一行全量输出(X/Y/mx/my/btn/s1/s2+SAT),
  直接引用本拍读数(省一次 I2C); 波形深挖撤回(NVIC 优先级实验与
  ORE 探针留在固件内无害)。

★ 教训: ①Java byte 参与位运算必须 &0xFF ②"帧损坏"归因前先打印
  损坏帧内容(区分传输损坏 vs 解析 bug——本次 43% 帧损坏实为解析错) ③
  竞争模型要设计判别实验, 不能沿单假设修到底 ④(码道)TXE 等待必须
  带超时, 防对端异常卡死主循环。
