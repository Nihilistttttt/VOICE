一、审计范围与基线状态

本次审计覆盖上次系统性架构审计（2026-10-12）之后新增/变化的代码：User/test_modes.c（MODE=0 手势栈，约 290 行主体）、Phone/pressure.c/h、Phone/ads1115.c/h、Common/Config.h、USB 描述符与 USBFS 设备栈相关改动。

重要基线事实（已核实）：

  • TEST_MODE 当前 = 0。码道（华为云 CodeArts Agent）的未提交改动把 HID 摇杆鼠标从测试模式 5 提升为正式模式 0（6 个文件的模式门机械替换 5→0），模式 5 退回为旧版 V2（麦克风+AOA）。该替换本身低风险，但尚未见她方构建验证。
  • 目录结构已回退为 WCH 标准布局：Common/（Config、hal_gpio、serial）、Phone/（各器件驱动）、User/（main + test_modes）、Core/Peripheral/Debug/Startup/USB_Host 为官方库。此前的 Board/Hal/App/Test/Sense 分层与 hosttest 宿主单测已不在工作区。
  • 资源占用宽裕：.text 26316 / 256K Flash（约 10%），.bss 5344 / 64K RAM（约 8%）。

二、审计发现（按严重度排序）

中F1 手势状态机全部内联，宿主单测安全网丢失

Mode_HidMouse() 一个函数内用约 18 个局部状态变量（ms_btn / sip_mode / rclick_pend / scroll_mode / s2_mode / home_seq / kb_pend …）承载 6 套互相耦合的状态机：s1 吹气、s1 吸吮、双口滚动、s2 手势、回主页序列、键盘两相发送。这正是 state-machine-design 技能列为反模式的"隐式状态"——每加一个标志就产生一批未测试的状态组合。

且：曾把状态机抽为纯逻辑 + 73 条断言的 Sense/gesture.c 与 hosttest/ 在目录重构中丢失（git 历史无删除记录，属丢失的 9 个 commit 之列）。现在改任何手势逻辑都没有回归安全网。

建议：先做与框架无关的第 0 步——把 6 套状态机重新抽成显式枚举 + per-state handler（技能 Pattern A），恢复到可在宿主编译单测的形态。这是后续任何框架迁移的地基。

中F2 总线故障静默：读失败与"真实零读数"不可区分

ADS1115_ReadReg() 失败时返回 0，ADS1115_ReadChannel() 也返回 0；Pressure_ReadCounts() 头注释自己注明了这一点。后果：I2C 总线死掉后，上层看到的是"两个口都没有压力"——设备外观完好但完全无响应，没有任何错误指示。对辅助器具这是最坏的失败形态（用户无法区分"没吹"和"坏了"）。

建议：驱动层增加带外错误通道（连续失败计数 / 错误标志 / 返回码区分），上层在 N 次连续失败后进入可感知的降级态（串口+OLED 指示，或指针周期性大幅抖动提示）。与 async-lifecycle 技能一致：异步标志必须有显式的错误出口。

低F3 回主页序列无断连恢复策略

home_seq 序列运行中若 USB 枚举丢失（拖拽、松线），重连后序列会从中断的那一相继续（例如指针已冲到角上、还没点下去）。无害但不优雅，且是未定义行为。建议：枚举状态跃迁时显式中止 home_seq（或从头重驱）。

低F4 阻塞式 Delay_Ms 超循环：时序与循环速率强耦合

整个 MODE=0 是一个 Delay_Ms(50) 阻塞循环，所有节奏都寄生在循环周期上：滚动 100ms/格 = 2 个循环、CLICKNAV 定位 25ms/帧 = 半个循环。上周的"飞太多"bug 根因就在此——宿主指针加速度把发送速度耦合进了位移，而发送速度只能靠调循环延时间接控制。功能越多，这种隐式时序越难维护。

这不是 bug，是架构特性，也正是本次框架选型要回答的核心问题。

低F5 驱动状态"最近一次读取"语义，多调用点隐式共享

Pressure_Saturated() 依赖 ReadCounts() 的副效应更新 s_sat1/2；打印块里又重复读一次。单线程超循环下成立，但调用顺序即正确性。建议改为显式传入读取上下文或返回结构体。

信息F6 文档漂移（小）

Config.h 中 HID_REQUIRE_PHONE 注释仍写"MODE=5 附加开关"，实际已服务于 MODE=0；ads1115.c 头注释"硬件版尚未独立验证"已过期（硬件 I2C2 早已转正并实测）。建议码道提交模式门改动时顺手更正。

做得好的部分（应予保留）：① pressure.c 换算公式有数据手册表6推导、整数运算避开浮点/64位除法、中位数零点校准、双向饱和钳位+SAT 标志，是本工程文档化最好的驱动；② ads1115.c 硬件 I2C 每步带超时与总线释放，ACK 时序修复有实测证据（612+365 次失败定位），A/B 传输开关设计干净；③ 两层配置模型（BOARD_HAS_*→USE_*+#error 一致性检查）方向正确；④ 码道的模式门替换是机械性低风险改动，未夹带行为变更。

三、Zephyr SMF vs QP™ 选型分析

3.1 候选方案的事实基线（已核实）

维度Zephyr SMFQP™（Quantum Platform）
定位轻量层次状态机库（~500 行，3 个 API：set_initial / run_state / set_state）。不是框架——无事件队列、无活动对象、无定时服务，调度仍是你的超循环事件驱动框架：活动对象 + 层次 UML 状态图 + 事件队列 + 发布订阅 + 时间事件（定时器）+ QS 软件跟踪 + QM 建模工具
RTOS 依赖零依赖，纯 C99，可独立抽取（第三方 tayne3/SMF 版 ~2KB .text、<96B RAM/实例，API 与 Zephyr 原版不兼容）裸机可运行（QV 协作内核替代超循环 / QK 抢占式 RTC 内核），本身不是 RTOS，不违反项目"不引 RTOS"红线；也可叠加在 RTOS 上
CH32V307 支持纯 C 库与芯片无关，直接可用官方提供主流 CPU 移植，无 CH32V307 现成移植；但 QP 移植层极小（临界段宏 + 时钟节拍），RV32 无 PRIMASK 需用 QingKe CSR 中断控制实现
USB 生命线无关（库不碰外设）无关（框架不碰外设；WCH USBFS 栈可保留为"服务"被活动对象调用）
测试工具纯 C 易宿主编译；但无专用测试/跟踪设施QUTest（宿主单元测试）+ QS/QSpy（目标端实时跟踪状态迁移，不停机）+ 桌面模拟开发。与本项目已有的 hosttest 文化天然契合
安全 pedigreeZephyr 子模块，社区广泛使用15+ 年，医疗/航空/国防在役，MISRA 友好，配套 QL 编码风格规范
授权Zephyr 为 Apache-2.0；第三方抽取版看各自仓库双授权：GPLv3 或商业授权。选 GPL 则整个链接固件须 GPL；闭源分发须购买商业授权（需向 state-machine.com 询价）
学习曲线平缓（半天）陡（活动对象/UML 状态图/控制反转，按周计）
必须同时看到的事实：Zephyr 上游已正式支持 CH32V307V-EVT-R1（GPIO/I2C/UART/SPI/DMA/Ethernet/EXTI/PWM 等），但板级支持列表中没有 USB 设备控制器驱动。因此"整体迁 Zephyr"路线对本项目基本关闭：① USBFS HID 复合设备是产品生命线，要么自己给 Zephyr 写 UDC 驱动，要么把 WCH 寄存器级栈塞进 Zephyr 驱动模型——两条都是深水区；② west/Kconfig/设备树构建体系替换 MounRiver，成本全项目级；③ Zephyr 是 RTOS，违反既定决策；④ 256K/64K 上跑完整内核性价比低。SMF 的正确用法只有"独立抽取版"这一种，而那样得到的只是一个层次状态机库，拿不到 QP 的事件队列/定时/跟踪生态。

3.2 与本项目的匹配度

把项目的真实痛点代入对比：

  • F1（状态机内联无测试）：两个方案都不直接解决——那是抽取+单测的功课。但 QP 的状态机写法（每个状态一个 handler、转移显式）天然强制结构化，且 QUTest 可直接宿主测试状态图；SMF 只提供容器，测试仍要自己搭。
  • F4（时序耦合）：QP 的时间事件（QTimeEvt）让"滚动 100ms/格""CLICKNAV 定位 25ms/帧"变成显式定时器，与主循环速率解耦——上周那类加速度耦合 bug 会从"调循环延时"变成"调一个定时器参数"。SMF 无此能力。
  • 功能路线图（下一大项是文字输入：摩斯/语音）：事件驱动 + 活动对象是这类多模态输入的自然架构；QP 的 QS 跟踪还能在真机上观察患者实际操作时的状态迁移，对辅助器具的体验调优价值很大。
  • 资源：QP/C 约 4–8KB ROM，QP-nano 更小；相对 10% 的 Flash 占用率完全不是问题。
  • 授权是 QP 唯一的硬伤：项目已在 GitHub 公开，若接受 GPLv3 则 firmware 整体开源（WCH 外设库许可证需一并核对兼容性）；若将来商业化，需购买商业授权。

四、结论与建议路径

结论：选 QP™（QP-nano 或 QP/C + QV 协作内核），不选 Zephyr SMF。理由：SMF 独立抽取版只是一个层次状态机库，解决不了本项目最痛的时序耦合与可测试性；整体 Zephyr 路线因 USB 驱动缺失、构建体系替换和 RTOS 红线而关闭。QP 以"非 RTOS 的事件驱动框架"形态，同时回应 F1/F4 与后续功能路线图，且其测试/跟踪工具链与项目既有 hosttest 文化同构。

但强烈建议分四步走，禁止一步到位（违反"不在同一次改动里既重构又加功能"的既定原则）：

  1. 第 0 步（无框架，立即做）：恢复丢失的安全网——把 6 套内联状态机抽为显式枚举 + per-state handler 纯逻辑模块，重建 hosttest 单测。这一步做完，F1 关闭，且无论将来用什么框架都受益。
  2. 第 1 步（试点）：修 F2（总线故障带外通道）与 F3（序列断连恢复）。这两项与框架无关，但都是可靠性硬伤。
  3. 第 2 步（引入 QP-nano 试点）：只迁移 MODE=0 控制层：s1/s2/滚动/回主页建模为活动对象，时间事件替换循环寄生时序；WCH USBFS 栈保持不动，作为被调用的"服务"。先评估移植工作量（RV32 临界段宏）与授权决策。
  4. 第 3 步（推广）：文字输入功能直接在 QP 上建；QS 跟踪用于真机行为调优；条件成熟时用 QM 建模复杂状态图。

什么时候反而该选 SMF：若团队明确拒绝 QP 的授权成本和学习曲线、且只想要"把状态机写整齐"——那就用独立抽取版 SMF（~2KB、Apache 系许可、零风险），但要知道它给不了事件队列、定时器和跟踪，F4 只能靠其他方式缓解。

五、未决事项（需决策/核实）

  • 授权决策：QP 走 GPLv3（固件整体开源，需核对 WCH 外设库许可证兼容性）还是购买商业授权（询价）。这决定第 2 步能否启动。
  • Zephyr USB 缺口：以上游 main 为准，CH32V307 移植未见 USB device 驱动；若 Zephyr 后续补齐，可重估"整体 Zephyr"选项（届时 QP 也可跑在其上）。
  • 码道未提交改动：模式门 5→0 替换的构建验证在她那边；本文档审计基于该改动后的工作区状态，未代为构建（避免触碰她的工作区）。
  • RV32 临界段：QP 移植需用 QingKe V4 的 CSR 中断开关实现 QF_CRIT_STAT，工作量小但需实测验证。
