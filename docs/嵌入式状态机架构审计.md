## 一、当前实现是什么样的(审计结果)

### 1.1 调度模型: 协作式 Super-Loop + TIM2 时间片轮询

```
while(1) {
    now = TIM2->CNT                      /* 100µs/计数, 自由运行 */
    Log_Service();  Cmd_Poll(1);
    EspLink_Poll();                      /* UART6 RX 环→帧解析(参数下行) */
    if (elapsed(sens) >= 50ms)  { 读压力×2; EspLink_SendWave(p1,p2); }
    if (USBFS_DevEnumStatus) {
        if (elapsed(hid) >= need_ms) {   /* HID 节流(回主页相有专节奏) */
            p1,p2 已就绪 → s1_sm_step / s2_sm_step / scroll_sm_step
            → 合成 mouse_report[5] → USBFS_Endp_DataUp(EP2)
            → home_sm_step / kb_sm_step → EP1
            → 每拍诊断行(20Hz)
        }
    } else { 200ms 节流的断连恢复 }
    Delay_Us(2000);
}
```

### 1.2 状态机清单(TEST_MODE=0 内共 7 个: 5 业务 + 2 协议/解析)

| 状态机 | 文件 | 职责 | step 驱动方式 |
|---|---|---|---|
| s1_sm | Services/gesture_sm.c | 单口手势(吹=左键/拖拽, 吸=中键/音量) | 主循环每 HID 拍直调 |
| s2_sm | 同上 | 双口手势(短吹=Alt+Tab, 短吸=回主页) | 同上 |
| scroll_sm(scr) | 同上 | 双口滚动(wheel ±1 限速) | 同上 |
| home_sm(hom) | 同上 | 回主页序列(多相) | 同上 |
| kb_sm(kb) | 同上 | 键盘报告两相(按下→释放) | 同上 |
| s_fstate | Services/esp_link.c:58 | WiFi 帧协议解析(找头→LEN→TYPE→PAY→CRC) | 主循环 EspLink_Poll 排空时逐字节 |
| param_parse_state | Services/phone_control.c:112 | USB CDC 参数解析 | 主循环轮询 |

> 前 5 台为 SMF 驱动; 后 2 台为手写 switch/if 状态机(协议/解析层), 未纳入 SMF。
> 故"系统内实现"的完整计数应为 7 个。(`mic_hum.c` 因 USE_MIC_HUM=0 未编入)

### 1.3 中断的现状: 只搬数据, 不置位任务

- **UART6 RXNE**: 单字节 → 环形缓冲(512B), 主循环 EspLink_Poll 排空解析。
  **无 ORE(溢出)检测**(ISR 仅 RXNE 分支), **无事件置位**——参数帧的"到达"
  是主循环轮询发现的。
- **USBFS**: EP2 IN 完成 → Busy=0(资源释放信号); SOF 分支空; 无事件 post。

**评价: 这恰恰是教科书写法**——"ISR 只做最短动作(清标志/搬数据/入队),
不做业务处理"。当前中断侧没有任何违规。

### 1.4 跨模块耦合点(风险清单)

| 耦合 | 位置 | 性质 |
|---|---|---|
| `mouse_report[5]` 共享缓冲 | test_modes.c 451-490 | **顺序敏感的多方写入**: s1/s2/scr 先写 → hom 序列后接管 → cons 覆盖。曾出"序列代码必须在正常赋值之后"的坑 |
| `scr.active` 旗语 | test_modes.c 436 | 滚动期间**直接冻结** s1 状态机(跨状态机直写旗语) |
| `hom.phase` 接管 | test_modes.c 470+ | 回主页序列直接覆盖 mouse_report |
| `USBFS_DevEnumStatus` 全局门控 | 主循环 | 未枚举时 HID 全停(传感器/波形已解耦 ✓) |

## 二、"正常应该怎么做"—— 最佳实践检索结论

### 2.1 业界共识(5 篇检索源交叉验证)

1. **每模块一个状态机 + 协作调度器**: 小 MCU 上"每个固件活动一个
   状态机(按键/LED/传感器/通信), 各持私有上下文, 主循环顺序给每台
   机器运行机会" —— **VOICE 已经是这个结构**(5 台机器 + super-loop) ✓
2. **ISR 职责**: 只做"计数/存环形缓冲/置标志/存采样值"—— **VOICE 中断
   侧完全符合** ✓
3. **事件队列**: "ISR 或轮询层把原始条件压缩成事件(BUTTON_PRESSED/
   UART_RX_READY/SENSOR_TIMEOUT), 调度器转发给关心的状态机" ——
   固定环形队列, 事件 ID + 小参数(联合体), 容量 8~32, **避免动态分配**。
   **VOICE 缺这一层**——目前靠主循环轮询+旗语。
4. **事件标志 vs 队列的选择**: "无序无数据的事件用标志(可合并); 有序
   带数据的用队列" —— 不是所有事件都要队列。
5. **跨状态机交互**: "**用显式事件, 不要直写对方状态变量**" —— scr.active
   直写冻结是反模式(但规模小时可容忍)。
6. **Run-to-completion**: 每个状态机 step 快进快出 —— VOICE 符合 ✓。
7. **软件 tick 树**: 1ms tick 挂 10ms/100ms/500ms 软件定时器 —— VOICE 的
   TIM2+elapsed 判断是等价实现 ✓。
8. **Active Object(FSM+线程+队列)**: 需要 RTOS —— VOICE 无 RTOS,
   **现阶段不需要**。
9. **"不可能事件"要留痕**: default 分支 unhandled_event_count++ ——
   可作为低成本改进。

### 2.2 对照表

| 最佳实践 | VOICE 现状 | 判定 |
|---|---|---|
| 每模块一个状态机 | 5 台机器, SMF 统一框架 | ✅ 已达标 |
| 协作调度器(非抢占) | super-loop + TIM2 时间片 | ✅ 已达标 |
| ISR 短(只搬数据) | UART7 环形缓冲/USB Busy 标志 | ✅ 已达标 |
| 事件队列(ID+参数) | ❌ 无, 靠轮询+旗语 | ⚠️ 缺口 |
| 跨机器用事件不直写 | ❌ scr.active 直写/hom 接管 | ⚠️ 缺口 |
| 显式枚举状态(非旗语组合) | s1/s2 显式枚举 ✓; scr.active 旗语 | ⚠️ 局部 |
| Run-to-completion | step 快进快出 | ✅ |
| 软件定时器树 | TIM2+elapsed 等价 | ✅ |
| Active Object / RTOS | 无 RTOS | ➖ 规模不需要 |
| default 留痕 | SMF 无 unhandled 计数 | ⚠️ 小改进 |

**总评: 主架构正确且已达标; 差距集中在"事件抽象"一层——不是错, 是
规模未到。**

## 三、演进建议(按投入产出排序)

### 档位 A: 保守修补(推荐, ~半天, 零风险)

1. **单一写入点**: 把 mouse_report 的合成改为"各状态机产出自己的
   out_t(btn/mx/my/wheel/cons 字段), 主循环末尾**按固定优先级合成一次**"
   ——消灭"序列代码必须在正常赋值之后"这类顺序陷阱。
2. **scr.active 旗语 → 事件**: 滚动机进入/退出时 post
   `EVT_SCROLL_ENTER/EXIT`, s1 收到后自行决定冻结(状态机自治)。
3. **SMF default 留痕**: unhandled 事件计数 + LOGD
   —— **勘误(2026-10-19): 当前不适用**。SMF 是"状态 run 每拍执行"模型,
   无事件分发, 因而没有"unhandled 事件"概念; 本移植版 SMF 的
   INSTRUMENTATION 关闭, 亦无官方 hooks(on_action/on_transition/on_error)。
   该机制属事件驱动改造的产物, 仅在引入事件队列后才需要。

### 档位 B: 事件队列(中等, ~2 天, 规模变大前值得)

4. 固定环形事件队列 `event{u8 id; u16 param}`(容量 16~32):
   - **生产者**: UART7 ISR(参数帧完成时 post EVT_PARAM_FRAME——现状
     是逐字节入环, 主循环轮询解析, 改为 ISR 组帧完成后 post 事件,
     主循环少一次轮询)、参数变更(EVT_PARAM_CHANGED, 波形阈值虚线
     联动/手势状态机刷新参数)、USB 枚举/断连(EVT_USB_READY/LOST)。
   - **消费者**: 主循环每次迭代排空队列, 按事件类型分发给对应状态机。
   - **收益**: 事件顺序保持、ISR 更短、状态机从"轮询全局"变"响应事件",
     新功能(如波形开关)只加事件类型不改循环结构。
5. 软件定时器树(1ms tick 挂软件定时器)——把散落的 elapsed 判断收拢
   (可选, TIM2 方案已够用)。

### 档位 C: 不建议现在做

6. Active Object + RTOS(FreeRTOS): 8 通道手势设备的复杂度尚未触线;
   RTOS 会引入优先级反转/栈 sizing 一类新问题, 现有协作调度完全够用。
7. 每状态机独立事件队列(完全 Actor 化): 过度设计, 共享
   mouse_report 的合成点天然需要集中。

## 四、回答用户的三个具体问题

**Q1: "正常会怎么做? 每个模块一个状态机?"**
—— 是, 且**你已经是了**(5 台机器+SMF)。业界术语叫"多状态机协作调度"。

**Q2: "状态机任务队列?"**
—— 正确形态是**一个共享事件队列**(不是每状态机一个队列): ISR/轮询层
post 事件, 调度器分发。VOICE 当前缺这一层, 但规模未到必须加的程度。

**Q3: "靠中断来置位任务还是干什么的?"**
—— 两种都正规: **事件标志**(无序无数据, 开销最低) 和 **事件入队**(有序
带数据)。原则: **ISR 内只置位/入队, 状态机在主循环上下文消费**——VOICE
的中断已经在这么做(搬环形缓冲), 只差把"数据到达"升级成"事件"。

## 五、本次波形卡顿与架构的关系(附注)

本次卡顿根因是 App 端 Java CRC 符号扩展 bug(解析层), **与主循环架构
无关**。但码道的 TIM2 重构(Poll/SendWave 拆分/HID 节流)顺带把架构的
最大隐患(Delay_Ms(50) 固定拍 + 冲角段忙等)修掉了——这与本审计的
"Run-to-completion/非阻塞"方向一致。
