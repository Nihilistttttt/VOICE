## 一、ESP8266 烧录与启动（2026-10-15/16）

### 坑 1: esptool 全变体超时 —— flash 芯片不响应

- **现象**: esptool 各变体（stub/no-stub、115200/74880）同步均成功（识别 ESP8266EX、MAC、stub 运行），但全部死于 "Enabling default SPI flash mode" 后第一条 flash 命令超时。
- **排除过程**: boot strap 全对（R34=GPIO15 下拉/GND、R32=GPIO0 上拉 3V3P、R33=EN 上拉）；串口双向链路通（sync 证明）；波特率/协议穷举。
- **根因**: ESP8266MOD 内集成 SPI flash 不响应——**用户修复（供电/焊点处理后恢复）**。flash 厂商 5e = **Puya**（Device 4016 = 4MB）。
- **解决**: 硬件修复后一次烧成。
- **预防**: ESP8266 烧录超时且 sync 成功时，先怀疑 flash/供电，再怀疑软件；`flash_id` 是最快的 flash 存活探针。

### 坑 2: Puya flash + ESP8266 core 的 boot 循环

- **现象**: 首次上传后无任何 [WIFI] 输出；115200 抓到乱码（重复模式）。
- **根因**: 乱码实为 **74880 波特率的 boot ROM 输出**被 115200 误读；boot mode:(3,6) = 正常 flash 启动，bootloader 加载完成 → app 在跑。
- **解决**: 抓串口必须**分段匹配波特率**——ROM 阶段 74880 可读、app 输出 2M（本 ino 用 Serial.begin(2000000)）。
- **预防**: 判断 ESP8266 死活用 74880 抓 ROM 行（`ets Jan 8 2013, rst cause:x, boot mode:(x,x)` 可读即 ROM 活）；app 崩溃用 `rst cause` 与加载段判断。

### 坑 3(意外收获): 一键下载电路

- **发现**: U4/U7 模拟开关之外，Q5(E=E_RTS,C=E_RST)/Q7(E=E_DTR,C=E_GPIO0) 把 CH340 的 RTS/DTR 接到 ESP8266 的 RST/GPIO0 —— **标准一键下载电路**。SW5 = ESP 手动复位键，SW4 = MCU 复位键。
- **意义**: Arduino IDE 直接上传（RTS/DTR 自动进 boot），零飞线零按键操作。

### 坑 4: "硬件孤岛"错误结论（重要教训）

- **现象**: 旧注释（serial.c）称"ESP8266 的 UART/控制脚未连 MCU（硬件孤岛）"。
- **真相（网表解析 hardware/电路.txt）**: ESP8266 经 **U4/U7 四路 SPDT 模拟开关**接 MCU；**CTRL0 由 SW3 机械开关**选择——CTRL0=0: CH340↔ESP8266（PC 直配/烧模组）；CTRL0=1: **CH340↔USART1(调试) + UART6(PC0/PC1)↔ESP8266 同时接通**。网名 `CH32_TX6/RX6` 的 "6" = **UART6**（CH32V307 有 UART6/7/8，IRQ 87-89）。
- **教训**: ①"网表核实过"也要核实核实者的结论；②判硬件孤岛前先搜模拟开关类元件（4052/4053/4066/TS5A/SPDT）；③嘉立创 EDA JSON 用 `components[key].props`（Designator/LCSC Part Name）+ `pinInfoMap`（引脚→网络）解析。

## 二、MCU 烧录链路（2026-10-15）

### 坑 5: OpenOCD 配置文件来源错误

- **现象**: flash driver 'ch32vx'/'wch_riscv_flash' not found。
- **根因**: `scripts/wch/wch-riscv.cfg` 是旧式 JTAG 模板（jtag newtap，不可用于 WCH-LinkE SDI）；**真正可用配置在 `bin/wch-riscv.cfg`**——`adapter driver wlinke` + `transport select sdi` + `wlink_set_address 0x00000000` + **target 类型 `wch_riscv`** + **flash bank 驱动名 `wch_riscv`**（expected-id 0x00001）。
- **解决**: 项目内固化 `VOICE_V307/flash_v307.cfg`（照抄 bin 版+注释）。
- **预防**: MounRiver fork 的 flash 驱动符号前缀（_ch32vx_*）≠ 注册名（wch_riscv）；以 bin/*.cfg 为准。

### 坑 6: "烧录后复位"认知修正

- **现象/误判**: openocd `reset run` 无效（本板 LinkE 未接复位线）→ 曾得出"烧录后需手动上电"的错误结论；甚至用 `mww 0xE000ED0C 0xBEEF0080`（PFIC 系统复位）+ resume 做过补偿——芯片反而停在 halt。
- **真相**: **`program ... verify` 成功（Verified OK）后芯片自动复位重启新固件**。早期"复位无效"是两次烧录失败（坑 5 驱动名错）造成的误读。
- **预防**: "烧录即复位"已写入规范；串口监听常驻 + SystemClk 启动标记轮转 = 烧录结果自动取证，不再靠猜。

## 三、串口与端口（2026-10-15/16）

### 坑 7: COM 口身份混淆（CH340=COM5，COM9 是 LinkE）

- **现象**: 调试日志一直用 COM9 抓；ESP8266 烧录时用户 IDE 用 COM5。
- **真相**: **COM5 = CH340**（VID 1a86:7523，接 USART1 调试口/按 SW3 切 ESP8266）；**COM9 = WCH-LinkE 的 CDC 虚拟串口**（也镜像 USART1，随 LinkE 插拔出现/消失）。两者内容相同但生命周期不同——**LinkE 不插时 COM9 消失，COM5 恒在**。
- **预防**: 常驻监听绑定 CH340(COM5)；每次操作前 `list_ports` 确认身份（看 VID 1a86:7523）。

### 坑 8: esptool.py 的 python 环境陷阱

- **现象**: 直接跑 Arduino 自带 esptool.py 报 "Pyserial is not installed"。
- **根因**: shebang/调用落到 **managed python（无 pyserial）**；系统 python（D:/InstallData/.../python.exe）才有 pyserial 3.5。
- **解决**: 显式用系统 python 全路径调 esptool.py。
- **预防**: 本机双 python 并存，串口工具一律用 `D:/InstallData/ProgrammingTools/Environment/python/python.exe`。

### 坑 9: 常驻串口监听的两个工具级坑（serial_log.py）

1. **断线崩溃**: 烧录/复位瞬间 COM 口消失（USB 重枚举）→ pyserial SerialException → 无重连逻辑直接退出。**修复**: try/except + 1s 重连循环，缓冲跨断线保留。
2. **轮转误触发**: 启动标记检测 `BOOT_MARKER in buf` 在标记已位于缓冲起点时**永远为真** → 每 0.5s 假轮转刷屏。**修复**: `rfind(标记) > 0` 才认定新启动（起点=当前启动不动作）。
- **预防**: 常驻串口工具的两大必备属性=断线重连 + "已含标记"必须判位置。

## 四、通信链路排障（2026-10-16）

### 坑 10: UDP 测试失败的时序坑（SW3 挡位）

- **现象**: UDP 参数帧发出后 MCU 无解析。
- **根因**: 测试时 SW3 在烧录挡（CTRL0=0）——UART6↔ESP 物理断开，帧到不了 MCU。用户事后发现"忘调挡了"。
- **解决**: 拨到 UART6 挡后全链路立即打通。
- **预防**: 双挡位系统的排障第一问永远是"开关在哪个位置"；esp_link 的 diag 行（rx 计数）就是为此设计——**rx 不涨 = 物理层断，rx 涨 = 协议层查**。

### 坑 11: 诊断计数对账法（有效方法论，记录推广）

- **做法**: esp_link 每秒输出 `diag rx=N`（IRQ 收到字节总数）。发 4 字节参数帧 → rx 精确 +4 = 逐字节到达的对账证据。
- **价值**: 把"通不通"变成"到了几字节"——中间任何一环的丢失都能被定位（本案例中 [WIFI] 状态行 40B/15s 的到达节奏直接证明了 UART6 RX 链路健康，从而把嫌疑收敛到挡位/时序）。
- **推广**: 任何新增通信链路都应在收发两端放字节计数诊断。

### 坑 12: 协议帧 id 记岔 —— 需要机器可读对照表

- **现象**: 手工发参数帧时把 debounce(id=10) 当成了 home_x_center(id=11)，导致 debounce 被钳位写入 10。
- **根因**: 16 参数的 id 顺序靠记忆。**钳位机制正常工作**（600→10，max=10），伤害被兜住。
- **预防**: 配置 App 开发前，从 `Services/params.c` 描述符表**导出机器可读 id 对照表**（App 直接引用，禁止手抄）；高价值参数可考虑帧尾校验和（v2 备选）。

### 坑 13: 后台串口监听进程在自动化会话中易被误杀

- **现象**: run_in_background 的监听任务多次被 SIGTERM（会话/命令超时连带），导致验证时"盲飞"（读的是陈旧日志）。
- **预防**: 关键验证前先确认监听存活（`tasklist`/日志 mtime），或用前台短窗模式（`& MONPID + kill`）保证与验证同生命周期；日志文件 mtime 是最快的活性检查。
